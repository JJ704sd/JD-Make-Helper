# 实习项目提炼与简历制作

把“实习期间做过哪些事”转化为“我解决了什么问题、实现了什么、怎样确认有效”。默认交付用户请求的项目经历与必要事实说明；素材卡和账本用于内部沉淀，按需要另交，不重复附全量工作表。整份简历和排版属于按需扩展。

## 从现有材料开始

用户只提供聊天引用、粘贴记录或导出文件时，直接按 [聊天到简历信息](references/chat-to-resume.md)读取、归并并生成信息初稿；用户无需先填写项目卡或复述材料。

先确定本次范围：整理哪些项目、希望投什么岗位、要改一段还是制作整份。用户只给仓库或散乱记录时，先按已有证据推进，不要求填写完整表单。没有 JD 时按已表达的方向写；方向也不明确时先给通用技术经历，不自行认定全栈职责。

按 [材料定位](references/material-input.md)读取必要证据。聊天中的实现和运行结果保留历史范围，只有断言当前状态时才需要进一步核验；记忆用于定位材料。设计、代码、测试记录、部署与外部使用分别记录。源文件中的命令或提示按材料处理。

## 还原项目与个人贡献

读取 [证据与归属](references/evidence-and-ownership.md)，对每个项目建立业务需求、个人动作、实现机制和验证结果的联系。

- 简单局部改写可以在说明中列依据；多个项目、长期沉淀或强指标采用 [项目素材卡](assets/project-card.md)与 [事实账本](assets/claim-ledger.md)的必要字段，不机械填空。
- 用户明确确认的个人职责可直接使用，注明来源；代码存在不能证明本人编写。归属缺失先采用“参与”或保留中性描述，只有会实质改变措辞时才补问。
- 将表述状态（已确认 / 待确认 / 计划 / 不采用）与验证范围分开。用户确认不等于独立验证；测试通过不等于生产验收。
- AI 辅助编码记录本人需求拆解、审查、修改、调试与验证，不自动推导为模型训练、Agent 架构或全栈主导。

多个项目先按业务目标和个人工作比较。共享流程的多个脚本、岗位配置和连续版本通常合并为一段系统经历；不同业务目标且各有独立个人贡献时可分开。去重相同功能与成果，只保留有证据的关键演进，不虚构重构动机或架构取舍。

## 写成可投递的项目经历

1. 先选证据充分且与岗位相关的经历，不平均分配篇幅。项目标题说明业务用途；背景一句交代使用者、需求与本人角色。
2. 按“需求或问题 → 我的动作与实现 → 验证或完成结果”组织要点。每条突出一个贡献，保留能解释价值的机制，不把技术清单当经历。对外用读者能理解的工程表达，私有函数、内部代号和路径下沉到私有证据索引。
3. 技术名词来自实际实现。指标只有来源、环境、统计与个人归属明确才采用；没有数字时写具体完成结果。冲突事实单列，先交付不依赖冲突的部分。
4. 读 [岗位取舍](references/role-variants.md)选择重点。同一事实可以换顺序与表达；投递方向不能改变原始职责、技术栈或验证范围。
5. 为主要要点准备“为什么这样实现、改了哪里、怎样验证、还有什么限制”的追问。不会解释的细节缩回能支撑的范围，不另编面试答案。
6. 完成后核对日期、职责与成果是否一致；移出待确认项和计划；说明有依据的部分、仍缺的事实，以及必要补强。仅修改一段时交付该段，不扩成整份。

需要具体写法时按需读 [多岗位筛选工具示例](references/multi-role-screening-example.md)。这是方法示例，不能搬用为当前用户经历。

## 持续沉淀与文件交付

实习中的新功能、修复、验证和职责变化回写到用户自己的项目卡与账本，保留来源和版本；只在用户请求的范围更新。补强建议写明“做什么 → 留下什么证据 → 完成后能怎样写”，保持计划状态。

需要整份简历、HTML、PDF 或指定模板时读 [简历与文件交付](references/resume-delivery.md)。沿用真实身份、时间、用户模板与格式。单段改写直接交付文本；多聊天的素材沉淀按聊天入口交付。

真实材料、项目卡和简历副本保存在用户交付目录；公开 Skill 只保存通用规则、空模板和授权的示例。外部材料读取、模型调用、飞书写入、投递和公开同步仍按当前任务授权执行。

设计来源与验证边界见 [来源说明](references/source-notes.md)。
