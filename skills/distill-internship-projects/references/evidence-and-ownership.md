# 证据、归属与技术表达

## 一条主张需要哪些事实

只记录影响最终措辞的字段：原始事实、来源与位置、时间、个人动作、实现机制、验证范围、候选表述和确认状态。源码可用仓库相对路径与函数定位；运行证据记录日期、环境、输入范围和结果。内部路径与原文留在私有账本，简历使用允许公开的抽象表达。

| 表述状态 | 用法 |
|---|---|
| 已确认 | 用户明确提供或材料支持；可进入成稿，但不代表第三方独立证明 |
| 待确认 | 职责、日期、技术、指标或来源有缺失/冲突；留在内部草稿或说明 |
| 计划 | 尚未完成的补强、功能或验证；不写入已完成经历 |
| 不采用 | 不准确、不相关或不适合公开；不进入成稿 |

另记验证范围，不能用“已确认”代替：设计说明、已实现、历史本地测试、当前本地/Mock 测试、真实外部联调、生产使用/验收。各范围独立，可以只确认其中一部分。没有运行记录时，只说实现或已有测试代码。

历史记录保留日期与旧版本；当前代码变化可能使旧结果失效。“当时验证过”与“当前仍通过”分开。无需为写简历自动运行会发送消息、修改业务数据或调用付费模型的脚本。

## 个人工作与团队结果

用户说“负责整个项目开发及 AI 辅助代码审查、调试和验证”时，可以采用“负责开发”；无需反复要求再确认。但“独立”“主导”“核心架构”仍须相应事实。本人只做接口联调时不写接口设计；只做测试时不把业务实现归给本人。

团队规模、客户数、营收与整体获奖可交代背景；个人成果只描述本人模块和动作。代码提交与文件存在可支撑实现范围，不能单独证明作者身份、全部职责或生产影响。

使用 AI 编程助手与开发 AI 应用分开：前者说明本人如何拆需求、检查生成代码、定位问题并验证；后者说明实际 API、检索、工具调用或评测。没有训练事实不写模型训练，没有检索实现不写 RAG。

## 合并项目与梳理演进

判断两个项目是否有同一使用者、业务目标、核心流程与共享实现。同一工具支持多个岗位、同一服务的批处理和 UI、同一模块的几次修复，通常组成一段经历。各子模块作为贡献点，不拆成重复项目。

不同目标且有各自完整个人贡献时可以分开；强弱悬殊时保留强项，不为了数量扩写。实习经历与项目经历重复时选择一个位置详细展开，另处只作背景。

从时间线挑一个有价值的演进，例如先完成解析，再解决重复任务和异常恢复。只有材料支持原问题与修改动作才写“为解决……引入……”。曾评估但未采用的方案用于面试讨论，不写成已实现。

## 指标与结果

强指标需要说明来源、输入/样本、环境、时间窗口、统计方法、前后基线和个人归属；只用事实所需部分。用户明确提供的完整测量可以采用并标注来源，不要求所有简历都重新压测。

缺失或冲突的数字不取更好看的一个。先用可信的完成结果，例如“完成重复提交与无效参数的本地接口验证”，同时列需要确认的指标。没有测量时不自动改成“显著提升”“大幅降低”。

本地耗时与线上响应分开；平均值、P95/P99、吞吐量和耗时下降分开。样本里未出现丢失只能说明该样本，不能写“零丢失”。测试用例数、代码行数或使用了某工具，本身不能证明质量提升。

## 这些技术主张需要额外核对

| 材料里出现的事实 | 可写范围与需要核对的内容 |
|---|---|
| SHA-256、任务键、数据库唯一约束 | 文件识别/幂等机制；哈希不是加密；需要实际约束与重复提交行为支持幂等 |
| 租约、心跳、锁、重试 | 写具体避免的冲突或恢复场景；使用锁不直接证明分布式安全，加重试不直接证明一致性 |
| LLM 返回 JSON 与字段校验 | 接口集成与结构校验；不等于语义正确、筛选准确率或消除幻觉 |
| HTTP 200、accepted、入队或本地记录 | 请求或处理阶段已完成；不等于外部接收或业务完成 |
| Mock、合成数据、单元测试 | 对应本地正常/异常路径；不等于真实生产联调 |
| 飞书/邮件/消息接口 | 区分调用实现、实际提交、回读校验与接收/使用确认 |
| 部署脚本、容器、迁移记录 | 可写相应实现或操作；没有运行及使用证据不写稳定线上服务 |

不确定的技术含义先核对用户实现或官方文档，再写因果关系。不要用更专业的术语包装尚未确认的事实。
