# 对照 JD 判断岗位匹配

用于判断用户自己的经历是否符合一个具体岗位，或为已授权的改写选择重点。只有分析请求时，交付分析；不顺带改简历、制作文件或投递。

## 从已有材料开始

读取用户给出的 JD 和已有简历、项目信息稿或事实账本。只有聊天材料时，先按 [聊天读取流程](chat-to-resume.md)提取相关事实，无需用户重新填写素材卡；本次输出仍由匹配请求决定。

只有职位名称时，请用户补充具体职责和要求，不猜学历、技术栈或实习时长。JD 片段可先分析已读部分，注明缺失范围。在线岗位保留 URL 和实际读取日期；打不开的页面不能写成已读取，历史截图不证明职位当前开放。

## 要求与证据分别记录

把 JD 拆为职责、明确必备条件、核心能力、加分项与申请约束，合并重复要求，保留决定判断的原文。公司宣传不算候选人要求；“优先”“了解”“熟悉”不能一律改成硬性门槛。

每项要求引用事实账本的稳定 ID 或原材料位置，并说明本人动作、实际技术和验证范围。旧简历中的候选措辞不是新证据；助手生成的方案、团队成果和相邻技术不能直接证明用户具备该能力。

| 匹配状态 | 采用条件 | 下一步 |
|---|---|---|
| 已匹配 | 现有事实直接支持该要求，且个人边界清楚 | 选入合适的经历，保留证据范围 |
| 表达缺口 | 相关工作与归属已有依据，但简历没有写清 | 在已授权的改写中补充表达 |
| 证据不足 | 材料有线索，但来源、归属或结果不足以支持要求 | 补具体记录或个人职责确认 |
| 真实缺口 | 用户明确确认尚未具备，或事实明确不满足条件 | 制定实践计划或调整目标 |
| 待确认 | 没有决定性信息，无法判断是否满足 | 只补问影响结论的事实 |

未出现某个关键词不能自动判为真实缺口。按 JD 要求的能力深度判断：“没用过 Redis”能说明没有使用实践，不能单独否定“了解 Redis”；基本认知仍需材料支持。会 React 可以讨论迁移到 Vue 的基础，但没有 Vue 经历时不能标为已匹配。完成本地接口测试可支持测试实践；岗位明确要求生产排障时，同一材料不足以支持该要求。

匹配状态与账本的表述状态、验证范围各自独立。例如，“参与接口开发”已确认，不代表满足“主导架构”；“已匹配本地测试能力”也不把验证范围升级为生产验收。

## 给出可解释的判断

先逐项判断硬性条件，再看核心职责与加分项。学历、在读状态、地点、到岗时间和实习时长等明确门槛单列，不能用其他技术优势抵消。未知门槛写待确认；未满足明确门槛时，不给无条件投递建议，也不猜招聘方会豁免。

采用“建议投递”“补充材料后投递”“谨慎投递”或“暂不建议投递”，说明促成结论的要求和证据。有决定性未知项时给条件式结论，明确什么信息会改变建议。不要用关键词数量计算百分比，也不预测录用概率。

简单分析直接在答复中给结论、矩阵与关键下一步。较长分析或需要复用时，在用户私有目录复制 [岗位匹配稿](../assets/jd-match.md)，记录 JD 来源、事实版本、要求—证据矩阵、硬性门槛和最多 5 项优先补强。缺失证据写“未提供”，不留成看似已有依据的空白。

## 与后续交付衔接

- 用户同时要求改写：仅将可采用事实及表达缺口交给经历改写，沿用原事实 ID；匹配分析不会把待确认事实改成已确认。
- 用户需要整份简历：按 [文件交付](resume-delivery.md)消费已确认且适合公开的事实；未完成的补强不进入成稿。
- 用户需要面试准备：围绕矩阵中的高风险要求整理可回答的追问与证据缺口，不替用户编造回答。
- 仅问适配度：到分析为止。后续建议不代表自动执行另一个任务，也不要求安装 ASu-skills。

具体判断示例见 [虚构 JD 对照](jd-matching-example.md)。
