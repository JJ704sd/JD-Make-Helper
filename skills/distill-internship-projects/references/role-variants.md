# 同一项目的岗位取舍

有具体 JD 时，先按 [岗位匹配](jd-matching.md)把要求与证据逐项对应，再据此选择经历。没有 JD 时，以下只是通用表达方向，不能据此推断具体招聘门槛或给出匹配结论。

| 投递方向 | 优先提炼的个人事实 | 常见的越界表达 |
|---|---|---|
| 全栈开发实习 | 前端交互、后端接口、数据持久化、联调与错误状态处理；有两侧实际贡献时说明链路 | 将桌面 UI 称为 Web 前端；因目标写全栈而接管队友的后端 |
| 后端开发实习 | API 契约、数据模型、任务状态、幂等、错误处理、查询或性能的具体实现 | 自动补 Redis/微服务/高并发/分布式架构 |
| 测试开发实习 | 可复现问题、风险场景、测试工具与 Mock、数据构造、断言和回归结果 | 有测试文件就称已执行；将单元测试写成生产端到端验收 |
| 运维开发实习 | 发布、观测、故障定位、恢复/回滚、自动化和权限处理的实际闭环 | 把本地服务启动写成生产高可用；把脚本配置写成长期稳定运行 |

同一项目调整标题、要点顺序和细节密度，保持事实账本不变。需要多个版本时先写共享事实，再针对目标分别选取，不为了每个岗位补一套不存在的技术栈。

## 材料较弱时怎么写

- 本人以页面为主：突出组件、状态、表单和实际联调；后端实践放入计划。
- 只有脚本或桌面应用：突出数据处理、接口、任务可靠性、UI 与工具交付，保持平台名称准确。
- 只有课程/个人项目：保留真实性质，写本人实现与本地验证，不补正式公司或真实客户。
- 做过验证但没有业务指标：写覆盖的风险与实际结果，不用虚构百分比。
- 项目主要由 AI 生成：写本人确实完成的需求拆解、审查、修改、调试与验证；没有理解的实现不写成熟练掌握。

## 追问与补强

主要要点应能回答：需求是谁提出的？本人负责哪里？机制如何工作？为何采用它？什么输入和异常验证过？结果在哪个环境成立？仍有什么限制？

仅有材料未出现的事实不能直接判定用户没做过。必要时列待确认；实际能力缺口才列计划。补强任务围绕现有项目，优先留下接口样例、正常/异常测试、修复前后复现、日志或部署/回滚记录。完成后按新证据更新账本与经历。
