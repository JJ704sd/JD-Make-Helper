# 虚构示例：从证据判断测试开发实习岗位

全部公司、岗位与事实均为虚构，用于说明判断方式，不能作为使用者经历或真实招聘信息。

## 原始材料

用户希望判断是否值得投递，明确要求先不改简历。

JD：本科在读；每周至少到岗 4 天、持续 3 个月；有 Python 开发与自动化接口测试实践；能协助 Docker 部署；了解 Redis 优先。

已有事实：

- F1：用户确认用 Python 负责一个数据整理工具。现有简历已明确写出语言与职责。
- F2：用户确认编写接口自动化测试；运行记录显示指定版本的 6 个本地 Mock 场景通过，简历只写“参与工具开发”。
- F3：聊天中助手生成 Docker 配置；没有容器运行结果，也没有本人使用或调试的确认。
- F4：用户明确说尚未学习或使用 Redis，也不了解其基本用途。
- F5：用户明确提供本科在读信息，未说明到岗安排。

## 可交付的分析

结论：补充到岗安排与 Docker 实践材料后再判断是否投递。Python 与本地接口测试已有依据；实习安排这一明确门槛仍待确认。Redis 是加分项，缺口本身不抵消已有实践。

| JD 要求 | 证据 | 匹配状态 | 理由或下一步 |
|---|---|---|---|
| 本科在读 | F5 的本人陈述 | 已匹配 | 采用用户明确提供的在读信息 |
| Python 开发 | F1 的职责确认与已有表述 | 已匹配 | 语言、工作内容与个人边界清楚 |
| 自动化接口测试实践 | F2 的本人确认与运行记录 | 表达缺口 | 工作已有依据但简历未写清；仅限该版本的本地 Mock 范围 |
| 协助 Docker 部署 | F3 的助手生成配置 | 证据不足 | 不能将文件存在写为本人完成部署；补实际运行与个人动作 |
| 了解 Redis 优先 | F4 明确否认相关学习、使用与基本认知 | 真实缺口 | 按加分项处理，补足对应认知并有依据前不写入技能 |
| 每周 4 天、持续 3 个月 | 未提供 | 待确认 | 单列硬性门槛，不能推断安排 |

优先补强：确认到岗安排；补 Docker 实践与本人职责；若用户之后要求改写，补充 F2 的接口测试表达。Redis 可列后续实践计划，不能直接补入现有经历。

此次只交付分析，不输出重写段落、修改 HTML 或记录已投递。F2 的事实状态和本地验证范围保持原样；F3 不因 JD 需要 Docker 就变成已确认。

## 条件改变时如何处理

- 如果用户明确每周只能到岗 2 天：门槛变为未满足，建议“暂不建议投递该岗位”，说明与 JD 的冲突；不以技术优势抵消，不猜招聘方会放宽。
- 如果 JD 改为“参与生产环境故障排查”：F2 的本地 Mock 结果不能证明生产排障能力；若没有其他材料，标为待确认，不将原测试结果升级为线上验收。
- 如果用户只说“没用过 Redis”：仍需确认是否了解基本用途，不能直接标为真实缺口；这与 F4 明确否认基本认知的材料不同。
- 如果只有“测试开发实习”这一标题：先请求具体 JD；可以继续整理已有事实，但不编造招聘条件或匹配分数。
