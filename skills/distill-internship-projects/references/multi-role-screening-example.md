# 示例：多岗位简历筛选与流程自动化

本例来自授权的项目材料及原作者确认，用于演示提炼方式；不能当作其他使用者的经历。岗位版本只改变表达重点，不增加职责或成果。

## 原始事实与合并判断

同一套 Python 工具支持资深全栈、全栈实习、运维开发和业务系统运维四类岗位，通过各自的规则与校验处理差异。共享流程为：文件分流与批次隔离 → 本地解析/OCR 和脱敏 → LLM API 逐项取证 → Python 校验与规则处理 → SQLite 持久化及人工复核导出 → 按授权归档飞书。

原作者明确确认负责项目开发，包括 AI 辅助编码后的审查、调试和验证。技术包括 Python、PowerShell、SQLite、PyMuPDF、RapidOCR、LLM HTTP API、lark-cli，以及 unittest/Mock；Tkinter 是桌面审阅界面。

四类岗位不是四个独立技术项目：业务目标、队列和数据处理共用，差异来自规则与输出契约。简历建议合并为“多岗位简历筛选与流程自动化”，把岗位差异作为规则模块化的证据。

## 面向开发实习

**多岗位简历筛选与流程自动化**

面向招聘简历初筛需求，负责开发基于 Python 与 SQLite 的多岗位筛选工具，统一文档处理、任务状态与结果导出流程。

- 将四类岗位的证据规则与输出校验模块化，使用 PyMuPDF、RapidOCR 实现本地解析及 OCR 兜底，接入 LLM API 取证，由 Python 完成结构校验与规则处理。
- 基于文件哈希、岗位和规则版本生成任务键，结合 SQLite 唯一约束、worker 租约与心跳管理重复任务和处理状态，支持批次隔离及中断后的恢复处理。
- 集成飞书文档与多维表格归档流程，实现导入后的回读校验，输出可追溯的人工复核材料；开发 Tkinter 桌面审阅界面。

投全栈岗位时如实说明桌面界面与接口/数据贡献；没有 Web 前端事实，不加入 Vue/React，也不把 Tkinter 写成 Web 技术栈。

## 面向测试开发实习

**多岗位筛选工具的异常处理与回归验证**

负责多岗位筛选工具开发及验证，围绕任务状态、模型响应和外部接口组织可复现的测试场景。

- 使用 unittest 与 Mock 编写任务入队、岗位/版本匹配及结果处理测试，覆盖重复任务、无效模型 JSON 和 worker 租约切换等异常路径。
- 为模型 API 与飞书流程构造接口返回，检查异常分流、状态持久化和回读校验行为；保留 Mock 验证与真实联调的边界。
- 将岗位规则、结构校验和人工复核状态分开，针对异常响应生成可追溯结果，避免把处理失败写成候选人不合格。

这版写的是已有测试与处理机制；只有对应执行报告明确时，才增加“回归通过”和具体数量。
